# Полный продуктовый и технический аудит Insta Model

Дата: 26 июля 2026

Статус: аудит без изменений исходного кода
Область: CJM, UX/UI, импорт контента, генерация изображений и видео, RunningHub/Ollama/Apify, хранение данных, тестирование и README.

## 1. Резюме

Приложение уже реализует основной полезный сценарий:

1. Загрузить локальные фото или видео либо импортировать Instagram-публикацию.
2. Выбрать материалы.
3. Создать или отредактировать промпт.
4. Запустить генерацию через RunningHub.
5. Получить локально сохранённый результат.

Сборка и существующие автоматические тесты проходят. Работа с локальными секретами, канонизация Instagram URL, переиспользование существующего импорта и временная сборка каждого импортируемого поста реализованы разумно.

Главное ограничение: текущая архитектура рассчитана на одну интерактивную сессию, а не на постоянную фабрику контента. Массовая генерация видео потребует не просто ещё одной кнопки, а введения правильной модели медиа, постоянной библиотеки и серверной очереди.

## 2. Ключевые выводы по CJM

### 2.1. Запуск и настройка

Приложение запускается и позволяет настроить Apify, Ollama и RunningHub. Однако настройки представлены техническими идентификаторами: `RH01`, `RH02`, workflow ID и node bindings. Пользователь не видит понятного назначения workflow, его готовности и результата проверки соединения.

### 2.2. Добавление контента

Локально можно выбрать несколько файлов. Их загрузка выполняется последовательно, но интерфейс не показывает отдельное состояние каждого файла.

Instagram принимает только одну ссылку на публикацию. Нет:

- многострочного ввода ссылок;
- предварительной валидации пачки;
- импорта профиля;
- ограничения количества публикаций;
- фильтра по типу контента;
- отдельного повторного запуска неуспешных элементов.

### 2.3. Выбор медиа

Одно исходное видео превращается в две независимо выбираемые карточки:

- первый кадр;
- Reel/video.

Это намеренно два самостоятельных материала для разных дальнейших генераций: первый кадр используется как фото, а Reel — как видео. Такое разделение корректно.

Проблема находится в правилах выбора: материалы должны оставаться независимыми, но пользователь должен выбирать либо первый кадр, либо видео, а не оба сразу. Сейчас их общая принадлежность одному источнику не используется для взаимного исключения.

### 2.4. Промпты

Повторная генерация добавляет новый полный документ к существующему. В интерфейсе не различаются действия:

- создать промпт;
- пересоздать;
- дополнить;
- отредактировать вручную.

Автоматический выбор Ollama-пресета скрыто зависит от порядка текстовых действий. Для видеогенерации аналогичной автоматической подготовки отсутствующего промпта нет.

### 2.5. Генерация изображений

Небольшие серии работают приемлемо. Результаты сохраняются после каждого успешного задания. Однако задания не имеют постоянной истории и не восстанавливаются после перезапуска.

### 2.6. Генерация видео

Несколько видео-заданий передаются одним HTTP-запросом и последовательно выполняются внутри него. Если позднее задание падает или отменяется, ранее скачанные результаты могут остаться на диске без регистрации в медиатеке.

### 2.7. Результаты

Генерируемое видео не получает thumbnail/first frame и не становится полноценным повторно используемым входом.

Нет постоянной пользовательской библиотеки с:

- историей импортов;
- коллекциями;
- поиском;
- фильтрами;
- источником и датой;
- статусом использования;
- управлением занимаемым местом.

## 3. Самые серьёзные проблемы

### P0. Нет взаимного исключения связанных фото и видео

Первый кадр и исходное видео должны оставаться двумя независимыми материалами, поскольку они используются в разных дальнейших генерациях.

При этом оба материала происходят из одного видеоисточника и не должны одновременно попадать в один пользовательский выбор. Сейчас эта связь не выражена как правило выбора, поэтому пользователь может отметить оба материала и получить неожиданную комбинацию.

### P0. Нет постоянной очереди

На сервере существует только одна активная операция в памяти. После перезагрузки страницы клиент теряет её состояние, а после рестарта сервера теряется связь с RunningHub task.

Activity Log показывает события, но не может быть источником состояния очереди.

### P0. Пакет видео сохраняется как единая операция

Результат каждой строки не фиксируется независимо. Частично успешная пачка может закончиться общей ошибкой и оставить незарегистрированные файлы.

### P0. Гонка при отмене

Клиент разблокирует интерфейс до подтверждения отмены сервером. Новый запуск может пересечься со старым и получить конфликт активной генерации.

### P0. Небезопасная конкурентная запись индекса

Индекс импортов читается и полностью перезаписывается как JSON:

- без блокировки;
- без схемной проверки;
- без временного файла и atomic rename;
- без защиты от двух одновременных записей.

### P0. Крупные файлы буферизуются в памяти

Локальные uploads, Instagram downloads, RunningHub uploads и downloads загружаются целиком в RAM. Для массового видео это создаст большие пики потребления памяти.

## 4. Варианты исправления критических проблем

## 4.1. Независимые материалы с взаимным исключением

### Вариант A — минимальная доработка

Добавить первому кадру и видео общий `selectionGroupId`. При выборе одного материала UI автоматически снимает выбор с другого.

Плюсы:

- небольшой объём изменений;
- быстро устраняет одновременный выбор;
- сохраняет два самостоятельных материала.

Минусы:

- правило действует только в клиенте;
- прямой API-запрос может обойти ограничение;
- job builder не понимает причину взаимного исключения.

Подходит как временная защита.

### Вариант B — независимые Material с общей группой источника

Ввести сущности:

```text
SourceAsset
  id
  source
  metadata

Material
  id
  sourceAssetId
  selectionGroupId
  mediaType: image | video
  kind: firstFrame | originalVideo | uploadedImage | generatedImage | generatedVideo
  filePath

WorkflowSlot
  id
  accepts: image | video | prompt
  required
  multiplicity
```

Первый кадр и Reel остаются двумя полноценными `Material`. Общий `selectionGroupId` означает, что в одном наборе выбора может находиться только один материал из группы.

Ограничение проверяется на трёх уровнях:

1. UI автоматически заменяет выбранный материал его альтернативой.
2. Job builder отклоняет набор, содержащий оба материала одной группы.
3. Сервер валидирует сформированные jobs перед отправкой в RunningHub.

Плюсы:

- полностью сохраняет требуемую независимость фото и видео;
- защищает правило не только в UI;
- источник и происхождение материала остаются известны;
- правило подходит для одиночных и пакетных генераций;
- в будущем в одну группу можно добавить thumbnail или другие производные материалы.

Минусы:

- потребуется миграция текущего индекса;
- потребуется единая серверная и клиентская валидация.

**Предпочтительный вариант: B.** Он соответствует фактической продуктовой логике: фото и видео остаются самостоятельными материалами, но система на всех уровнях гарантирует выбор только одного из них. Вариант A защищает лишь интерфейс и может быть обойдён через API или ошибку в job builder.

### Вариант C — не связывать материалы, ограничить выбор только типом workflow

Фото и видео никак не связываются. Если выбран image-workflow, система разрешает только изображения; если video-workflow — только видео.

Плюсы:

- почти не требует изменения модели данных.

Минусы:

- не работает для workflow, принимающих одновременно разные типы входов;
- не предотвращает попадание связанных материалов в общий batch;
- теряется происхождение первого кадра.

Не рекомендуется.

## 4.2. Постоянная очередь генерации

### Вариант A — JSON queue с mutex и atomic write

Сохранить очередь в отдельном версионированном JSON-файле. Все операции проходят через один серверный `QueueStore`, сериализуются process mutex и записываются через:

```text
validate → write temp → fsync temp → rename → fsync directory
```

Дополнительно необходимы:

- backup последней корректной версии;
- runtime schema validation при чтении и перед записью;
- уникальный `jobId` и `idempotencyKey`;
- сохранение `providerTaskId` сразу после создания RunningHub task;
- архивирование старых terminal jobs, чтобы активный файл не рос бесконечно;
- startup recovery для незавершённых состояний.

Плюсы:

- минимум новых зависимостей;
- не требует миграции на базу;
- хорошо соответствует локальному однопользовательскому приложению;
- файл легко просмотреть, скопировать и восстановить вручную.

Минусы:

- все изменения должны проходить только через один `QueueStore`;
- нет транзакций между несколькими JSON-файлами;
- с ростом истории файл станет неудобным.

**Выбранный вариант: A — постоянная JSON-очередь.** Он соответствует текущему масштабу и сохраняет простоту установки. Вариант безопасен при условии одного серверного процесса, централизованной записи, atomic replace, резервной копии, строгой схемы и startup recovery. Если приложение станет multi-user или появятся несколько worker-процессов, очередь потребуется перенести в транзакционное хранилище.

### Вариант B — SQLite

Создать таблицы:

- `assets`;
- `renditions`;
- `generation_jobs`;
- `generation_attempts`;
- `generation_outputs`;
- `import_batches`;
- `import_items`;
- `collections`.

Worker выбирает `queued` jobs, фиксирует provider task ID и сохраняет каждый переход состояния транзакционно.

Плюсы:

- транзакции и конкурентная безопасность;
- простое восстановление после рестарта;
- удобная история и фильтрация;
- не требует отдельного сервера.

Минусы:

- понадобится миграция существующего JSON;
- нужно ввести слой репозиториев.

SQLite остаётся возможным следующим этапом, если JSON-история и количество связей станут неудобными, но не входит в выбранную P0-реализацию.

### Вариант C — Redis/BullMQ

Плюсы:

- развитая промышленная очередь;
- retry, concurrency и scheduling.

Минусы:

- отдельный сервис и более сложная установка;
- избыточно для локального приложения.

Имеет смысл только при переходе к сетевому multi-user сервису.

## 4.3. Независимое сохранение видео

### Вариант A — один клиентский запрос на каждую строку

Клиент самостоятельно запускает задания с ограничением concurrency.

Плюсы:

- относительно мало серверных изменений.

Минусы:

- закрытие вкладки ломает очередь;
- нельзя надёжно восстановить прогресс;
- бизнес-логика остаётся на клиенте.

Не рекомендуется как постоянное решение.

### Вариант B — серверный worker

Клиент одним запросом создаёт jobs и сразу получает их ID. Worker независимо:

1. подготавливает входы;
2. загружает их;
3. создаёт RunningHub task;
4. сохраняет task ID;
5. опрашивает состояние;
6. скачивает результат;
7. создаёт Asset и thumbnail;
8. переводит job в `succeeded`.

Ошибка одной строки не влияет на остальные.

**Выбранный вариант: B — серверный worker вместе с постоянной JSON-очередью.** Только сервер может продолжать работу после закрытия или перезагрузки страницы. Отдельный job на каждый результат позволяет независимо сохранять успех, повторять ошибку и восстанавливать RunningHub task по provider task ID.

Для текущего приложения worker может быть фоновой службой внутри того же Node.js-процесса, а не отдельным OS-процессом. Важно, чтобы он не зависел от жизненного цикла HTTP-запроса: API только создаёт jobs и возвращает их ID, после чего worker самостоятельно исполняет очередь.

## 4.4. Исправление отмены

### Вариант A — ждать завершения текущего cancel endpoint

Клиент сохраняет блокировку, пока запрос отмены не вернёт ответ.

Плюсы:

- небольшое изменение;
- устраняет немедленный повторный запуск.

Минусы:

- оборванный или зависший HTTP-запрос оставляет UI в неопределённом состоянии;
- состояние отмены по-прежнему не переживает перезагрузку.

### Вариант B — постоянное состояние `canceling`

Ввести переходы:

```text
running → canceling → canceled
                    → failed
```

После нажатия Cancel:

- не разблокировать новый запуск немедленно;
- показать `Отмена…`;
- дождаться подтверждения сервера;
- отдельно разрешить отмену queued и running jobs;
- не удалять уже успешные результаты.

Состояние сохраняется в очереди. После рестарта worker повторно проверяет RunningHub task и завершает переход.

**Выбранный вариант: B — постоянное состояние `canceling`.** Он устраняет не только визуальную гонку, но и рассинхронизацию между клиентом, локальным сервером и RunningHub. Такой подход естественно встраивается в постоянную JSON-очередь и корректно работает после перезагрузки.

### Вариант C — считать отмену локальной

Приложение прекращает polling и помечает job отменённым, не проверяя внешний task.

Плюсы:

- простая реализация.

Минусы:

- RunningHub может продолжить работу и списать ресурсы;
- готовый результат будет потерян;
- локальный статус станет недостоверным.

Не рекомендуется.

## 4.5. Хранение и миграция

### Вариант A — укрепить JSON

- runtime schema validation;
- автоматический backup;
- process mutex;
- запись через `temp → fsync → rename`;
- восстановление из последнего корректного backup.

Также необходимы:

- поле `schemaVersion`;
- единый модуль `JsonStateStore`, через который проходят все записи;
- запрет прямой записи JSON из route handlers и worker;
- проверка ссылок на существующие файлы при старте;
- reconciliation для случаев, когда файл результата сохранён, а индекс ещё не обновлён;
- ограничение размера активных файлов и архивирование истории.

**Выбранный вариант: A — укреплённое JSON-хранилище.** Для одного локального серверного процесса этого достаточно и оно не добавляет новую технологию в установку. Критическое условие: JSON нельзя считать просто файлом, который можно перезаписать из любого места. Он должен использоваться через единый сериализованный storage layer с проверкой схемы, atomic replace, backup и восстановлением.

### Вариант B — SQLite с однократным импортом JSON

При первом запуске новой версии:

1. создать базу;
2. прочитать текущий индекс;
3. проверить каждую запись;
4. импортировать транзакционно;
5. сохранить исходный JSON как backup;
6. записать версию миграции.

SQLite остаётся резервным путём миграции, если появятся несколько процессов, multi-user режим, сложные выборки или объём истории, при котором архивирование JSON перестанет быть удобным.

## 4.6. Streaming I/O

### Вариант A — сохранить буферизацию, ограничить размер и concurrency

- уменьшить максимальный размер файла;
- разрешить только одно видео одновременно;
- заранее проверять `Content-Length`.

Плюсы:

- минимальные изменения.

Минусы:

- RAM всё равно зависит от размера файла;
- проблема вернётся при увеличении лимитов.

Подходит только как временная защита.

### Вариант B — полный streaming pipeline

Рекомендуемая схема:

- входящие uploads сразу писать во временный файл;
- downloads проводить через stream pipeline;
- RunningHub upload читать файловым stream;
- проверять Content-Length и фактический размер;
- вводить лимит свободного места;
- удалять незавершённые временные файлы;
- считать checksum после сохранения.

**Выбранный вариант: B — полный streaming pipeline.** Видео потенциально значительно больше изображений, поэтому batch-функция быстро сделает буферизацию источником нестабильности. Streaming ограничивает потребление RAM, позволяет корректно прерывать операции и безопасно удалять частично загруженные файлы.

### Вариант C — отдельный процесс для файловых операций

Загрузки и скачивания выполняются специализированным worker-процессом.

Плюсы:

- сбой обработки файла не завершает основной API;
- можно независимо ограничивать ресурсы.

Минусы:

- усложняет локальную архитектуру;
- сам по себе не отменяет необходимость streaming.

Может быть добавлен позднее, но не заменяет вариант B.

## 5. Предлагаемый пакетный UI

Основное действие: `Создать пакет видео`.

Оно открывает Queue Builder с режимами:

1. `1 к 1 по порядку`: N фото + N видео = N заданий.
2. `Одно фото для всех видео`: 1 × N.
3. `Одно видео для всех фото`: N × 1.
4. `Все комбинации`: N × M с заметным предупреждением.

Перед постановкой в очередь показывается таблица:

- изображение;
- видео;
- workflow;
- промпт;
- готовность обязательных входов;
- статус проверки;
- действие исключения.

Над таблицей показывается итог:

```text
20 видео × 1 изображение = 20 заданий
```

Очередь должна поддерживать:

- pause/resume;
- cancel;
- retry failed;
- изменение приоритета queued jobs;
- фильтры по статусу;
- просмотр provider task ID;
- открытие готового результата;
- восстановление после перезагрузки.

## 6. Импорт пачки ссылок

Экран `Импорт` следует разделить на:

Apify direct URLs лучше группировать по типам результата. Posts/carousels и reels можно собирать отдельными actor runs, затем объединять результаты.

## 7. Импорт аккаунта

Форма:

- URL профиля или `@username`;
- количество 1–100, по умолчанию 20;
- `Все / Фото и карусели / Reels`;
- необязательное ограничение по дате;
- политика дублей;
- название коллекции.

Для режима `Все`:

1. запросить последние N posts;
2. запросить последние N reels;
3. объединить по времени;
4. удалить дубли;
5. оставить последние N.

До запуска показать:

- ожидаемое количество;
- число уже имеющихся локально;
- ориентировочное число внешних запусков;
- оценку расхода;
- ограничение для приватных аккаунтов.

Импорт должен создаваться как постоянный `ImportBatch`, а не удерживать открытый HTTP-запрос.

## 11. Рекомендуемый порядок реализации

### Этап 1 — контракты состояния

1. Зафиксировать схему `GenerationJob` и допустимые переходы состояний.
2. Добавить `schemaVersion`, `jobId`, `idempotencyKey`, `providerTaskId`, timestamps, attempts, input snapshot, output references и структурированную ошибку.
3. Ввести независимые `Material`, связанные через `SourceAsset` и `selectionGroupId`.
4. Добавить декларативные `WorkflowSlot` и серверную проверку подготовленных jobs.

Сначала фиксируются контракты, потому что JSON queue, worker, recovery и UI должны использовать одинаковую модель состояния.

### Этап 2 — укреплённый JSON storage

1. Создать единый `JsonStateStore`.
2. Сериализовать записи через process mutex.
3. Добавить runtime schema validation.
4. Реализовать `temp → fsync → rename` и fsync директории.
5. Хранить backup последней корректной версии.
6. Добавить восстановление из backup и понятную диагностику повреждения.
7. Запретить прямую запись state-файлов из route handlers, import pipeline и worker.
8. Разделить активное состояние и архив, чтобы рабочие JSON-файлы не росли бесконечно.

Этот этап выполняется до очереди, иначе новая очередь унаследует текущие риски конкурентной записи.

### Этап 3 — streaming primitives

1. Перевести локальные uploads на временные файлы.
2. Перевести Instagram/Apify downloads на stream pipeline.
3. Перевести RunningHub upload и download на streams.
4. Добавить AbortSignal, timeouts, проверку размера и свободного места.
5. Реализовать очистку незавершённых временных файлов.
6. Добавить атомарное перемещение готового файла в постоянное хранилище.

Streaming лучше внедрить до worker, чтобы исполнение jobs сразу использовало безопасный файловый путь и не потребовало повторного переписывания.

### Этап 4 — постоянная JSON-очередь

1. Создать отдельный версионированный файл активной очереди.
2. Реализовать операции create, enqueue, claim, transition, retry и archive через `QueueStore`.
3. Сохранять input snapshot до постановки job в очередь.
4. Сохранять RunningHub task ID немедленно после успешного создания внешней задачи.
5. Добавить startup recovery:
   - `queued` остаётся в очереди;
   - `preparing/uploading` без task ID безопасно повторяется либо переводится в failed;
   - `submitted/running` с task ID продолжает polling;
   - `downloading` повторно проверяет временный и итоговый файл;
   - `canceling` повторно проверяет состояние и завершает отмену.

## 12. Рекомендуемый целевой вариант

С учётом выбранных вариантов итоговая комбинация:

- React остаётся клиентом;
- Express остаётся локальным API;
- один локальный Node.js-процесс содержит API и фоновый server worker;
- постоянная очередь хранится в отдельном версионированном JSON-файле;
- существующие индексы остаются JSON, но все записи проходят через единый `JsonStateStore`;
- каждый JSON-файл защищён mutex, runtime-схемой, atomic replace и backup;
- активные jobs отделены от архивной истории;
- первый кадр и Reel остаются самостоятельными `Material`, связанными через `SourceAsset` и взаимоисключающий `selectionGroupId`;
- каждый результат исполняется и сохраняется как отдельный `GenerationJob`;
- состояние `canceling` хранится постоянно и восстанавливается после рестарта;
- RunningHub task ID фиксируется сразу и используется для recovery;
- uploads и downloads выполняются через полный streaming pipeline;
- файлы остаются в `data/`, а JSON хранит метаданные, связи и состояние;
- thumbnail/first frame создаётся локально для каждого готового видео;
- Apify import работает через постоянные batches;
- UI строится вокруг `Library`, `Recipes` и `Queue`.

### Почему комбинация подходит текущему продукту

- не добавляет SQLite, Redis или внешний сервер;
- сохраняет переносимость и простую локальную установку;
- поддерживает восстановление после перезагрузки;
- изолирует ошибку одного видео от остальных;
- ограничивает потребление RAM на больших файлах;
- позволяет реализовать batch-видео поверх уже устойчивых jobs.

### Обязательные ограничения выбранного JSON-подхода

- только один процесс имеет право изменять state-файлы;
- все записи проходят через один storage layer;
- worker нельзя масштабировать на несколько процессов без смены хранилища;
- операции, затрагивающие файл результата, media index и job state, требуют startup reconciliation, поскольку общей транзакции между ними нет;
- завершённые jobs необходимо регулярно переносить в архив;
- backup не заменяет полноценную пользовательскую резервную копию каталога `data/`.

### Условия будущего перехода с JSON

Переход к SQLite или другому транзакционному хранилищу потребуется, если появится хотя бы одно из условий:

- несколько server/worker процессов;
- multi-user режим;
- очень большая история jobs и импортов;
- сложные фильтры и связи между коллекциями;
- частые конкурентные изменения разных индексов;
- необходимость транзакционно изменять несколько сущностей.

В текущих границах — один пользователь, один локальный сервер и ограниченная concurrency — выбранная комбинация обоснована и не требует полного переписывания приложения.
